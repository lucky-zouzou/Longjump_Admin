# 每日经营行动单（第一阶段）

入口：`/?page=business-actions`，日常工作菜单。管理员、五站 TikTok/Shopee 运营、运营主管、财务和供应链可见；运营仅看本站渠道。工厂、海运、线下销售账号不能读取此模块或其接口。供应链不接收财务成本明细、销售金额、单位贡献及收益金额，保留盈利状态与补货依据。

## 责任与操作

三类行动分别由运营（财务核算）、供应链（运营协作）、站点运营主责。上线初始只显示主责岗位，**不猜测或自动分配具体人员**。管理员逐单确认唯一负责人、协作人、截止和复查时间；负责人须为有效账号，运营必须匹配国家与平台。默认待确认时间为首次识别后24小时截止、72小时复查，可明确调整。

操作：更新证据 → 管理员分配 → 负责人开始跟进 / 登记执行 → 到期复查 → 继续跟进或复查解决。弱动销在登记执行前必须记录流量、转化、价格、质量四项诊断和措施；缺资料应写明待核实。执行必须提供凭据编号或链接。财务复查亏损；供应链复查断货；本站运营或运营主管复查弱动销，管理员可监督复查。

同一国家＋平台＋SKU＋问题类型只保留一个永久行动编号。刷新更新证据，不按日期复制行动。信号缓解不会自动结案；执行后至少24小时、复查时间到期、有执行后新完整日数据且规则不再触发，才能登记解决。仍未解决需要下一次截止与复查时间。重新出现同类问题，或新期间证据不足时重开原单，进入已触发／待核实队列并保留历史，不会把历史已解决当作当前仍安全。首页待办按责任聚合为一项，避免刷屏。

最初只因资料不足而生成、经核实从未触发的记录，可以由对应复查岗位“核实排除”，提供完整证据及说明，不要求虚构执行。曾经确认触发的记录不能通过此入口绕过执行与复查。页面将信号缓解的记录单列待核对队列，避免挤占今天真实触发问题的位置。

## 数据与计算规则

覆盖五站线上销售。以各站点当地昨天为截止（印尼、泰国、越南 UTC+7；马来西亚、菲律宾 UTC+8），不包含今天未结束的数据。近7天与前7天是连续自然日。只有完整日报／确认零销售日报算完整覆盖；缺报、部分报表与冲销记录不能当作零销量。毛销量不与退货抵消。库存为账面可售减预留，不纳入待上架或隔离。线下销售不并入本模块线上贡献核算。

- **越卖越亏**：近7天实际成交额减系统滚动汇总的本SKU逐日到岸商品成本、广告、平台佣金及支付、履约、未在成交额扣除的退款与售后净成本。是经营贡献，未扣公司固定费用及所得税，不称净利润。折扣已在成交额，不再重复扣。财务填写实际归属的原币费用，全部未知时留空；只有确认无费用才能填0。绝不把全店广告费复制到SKU，或自动按销量分摊。每个国家＋平台＋SKU＋经营日期留存五类原币成本及凭据；近7天自动汇总，跨天复用其中6天。与该日销售、完整度、整店广告及售后退款依据绑定；源数据变化只把受影响日期标为需复核，不要求重填其余日期。财务修订追加版本，保留旧成本、凭据、说明及当时依据；新版本自动参与滚动重算。旧版7天合计仅保留历史，不虚构拆分为7份每日成本。非站点本币或缺金额先核实，不强行折算后认定利润。止损后完整日报确认零销量，仍需财务核实是否留有广告等费用；确认无持续损失后才允许复查结案。
- **盈利款快断货**：需核实正贡献、最近7个已结束自然日的完整销量。直接使用 `loadForecast` / `forecastPlan` 的7/21/56天加权需求、需求修正、供参、逐日到货曲线及约束后的补货量，不另算7日均值。逐日以可售＋当日有效到货－当日需求计算未满足量；销售丢失不当作待交付欠单，次日不会继续消耗后续来货。未知／逾期ETA不能当作今天到货。若缺完整日报、库存为负或在途ETA无效，确定补货量为空，显示待核实。周期外到货不抵扣本期需新增生产量；共用预测若混有线下实发需求，保留缺口但不套用线上单位贡献估算线下损失。已有生产量仍扣除避免重复下单，但无明确交期不能消除近期缺口；需先核对、加急或调拨。
- **积压款动销变弱**：两期14天完整日报且有连续上架可售证据；近7天比前7天下降至少30%，同时当前库存覆盖≥60天，或近7天确认零销量。零销量、不足14天在售、缺报与缺货分开。没有库存年龄数据时不认定历史呆滞年限。售后反馈只列记录数，不冒充退货率；流量、转化、竞价尚未接平台数据，需要运营提供报表依据，再选择素材、投放、描述、质量整改或清货方案，不能一律降价。

## 优先级与监督

先区分有证据触发、待核实、缓解待复查及已解决，再按最迟行动日优先，同日比较证据等级与未来7天可避免损失情景上限；GMV和日利润大小不作为首要排序。断货最迟行动日＝首个逐日缺口日－生产运输准备期；不足准备期时标今天需补救。亏损与动销诊断标今天处理。此建议日期和管理员人工设定的承诺截止时间分别显示，不暗改已分配责任与期限。跨币种仅使用已有有效CNY参考汇率，最多7天缓存；汇率无效时收益金额未知，不把原币大小混排。参考汇率不是财务结算汇率。

亏损情景：拖延一天损失＝核实7天亏损÷7，未来7天可避免损失上限＝本期亏损，假设销量成本保持不变。断货情景：明日风险贡献＝明日未满足量×核实单位贡献；未来7天风险贡献＝每日未满足量之和×核实单位贡献。库存曲线以当前库存为起点（第0天），从明天起计未来7天需求；假设有有效ETA的货物当日开始即可售，到货恢复后未满足量归零，不继续累计损失。动作不保证回收该金额。弱动销没有可核实的措施效果时不预设收益，显示待核实。

页面分为已触发、待核实、待分配、待复查、已解决队列，展示负责人、到期状态、协作人、原始核算来源、执行及复查前后证据。当前解释来自确定性规则与人工记录，**没有把业务数据发送给外部AI**。本轮不增加页面或AI功能。

## 运行、存储及验证

`GET /api/business-actions`只读；`POST`明确刷新或人工动作。Node后台启动并每10分钟刷新，在站点午夜跨期后更新；用户可主动更新。源数据版本时钟防止读取过程中变化，以及核算／复查事务期间的竞争；行动记录使用乐观版本防覆盖。数据刷新事务不更改销售、库存、广告、价格、采购或付款。

迁移 `0026_business_actions.sql` 新增行动、财务核算、事件轨迹和源版本表。所有业务写入遵循维护锁，四表纳入既有全量备份恢复；版本时钟懒初始化，避免恢复时冲突。具体负责人确认、诊断、财务、执行、复查、重开均留痕。

验证：规则与真实SQLite迁移、权限、并发、备份恢复测试在 `tests/business-actions.test.mjs`；本地接口及桌面／手机页面验收。第一阶段不连接广告／商品变价接口，也不创建采购指令。

## 日报与重复导入保护（0028）

现有销售模板是 SKU 日汇总，没有平台订单行唯一号，无法证明两份同日同 SKU 报表不重叠。同站点＋渠道＋日期＋SKU 的有效正销量已存在时，新批次整批拒绝；换文件、改批次名、改数量、拆分SKU集合均不能绕过。后台预检给出原因，数据库触发器在事务内兜底，竞争失败时连同其他SKU和库存流水整批回滚。同批文件内拆行仍按现有规则归并；不把 SKU 当成跨日期或跨店唯一键。

半天转全天或累计报表变化，通过既有“导入历史 → 修订”填写累计正确销量；原批次冲销与新批次写入同一事务，只产生净差额。冲销后可重新导入。不同SKU的分批报表可分别登记，最后核对整日。选择“完整日报”还须显式确认，且必须是站点已结束日期；否则保存为部分日报。当前日不进入需求预测。

历史记录不擅自清除或重扣。发现旧数据同一天同SKU跨多个有效批次时，完整度也按待核实处理，需核对原始订单后修订。财务与预测均拒绝用这些日期给出确定结论。

`business_action_finance_days` 按日、版本保存，追加写入，禁止原地更新和删除；纳入维护锁、源数据版本校验及既有全量备份。`GET /api/business-actions?id=...&financeDay=YYYY-MM-DD` 仅财务和管理员可读历史核算，保存仍仅财务。供应链响应中不包含每日成本或凭据。测试覆盖改名重叠、部分重叠、并发回滚、半天修订、完整度、共用预测、到货停止计损、紧急小款优先、跨日复用、退款/成本修订及权限。

月度人工备货仍可提交并保留人工数量；无完整预测的快照在接口、复盘和导出中显示待核实，不参与预测准确率。旧表非空数字列仅保留兼容占位，模型 JSON 保留未知状态。
