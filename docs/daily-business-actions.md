# 每日经营行动单（第一阶段）

入口：`/?page=business-actions`，日常工作菜单。管理员、五站 TikTok/Shopee 运营、运营主管、财务和供应链可见；运营仅看本站渠道。工厂、海运、线下销售账号不能读取此模块或其接口。供应链不接收财务成本明细、销售金额、单位贡献及收益金额，保留盈利状态与补货依据。

## 责任与操作

三类行动分别由运营（财务核算）、供应链（运营协作）、站点运营主责。上线初始只显示主责岗位，**不猜测或自动分配具体人员**。管理员逐单确认唯一负责人、协作人、截止和复查时间；负责人须为有效账号，运营必须匹配国家与平台。默认待确认时间为首次识别后24小时截止、72小时复查，可明确调整。

操作：更新证据 → 管理员分配 → 负责人开始跟进 / 登记执行 → 到期复查 → 继续跟进或复查解决。弱动销在登记执行前必须记录流量、转化、价格、质量四项诊断和措施；缺资料应写明待核实。执行必须提供凭据编号或链接。财务复查亏损；供应链复查断货；本站运营或运营主管复查弱动销，管理员可监督复查。

同一国家＋平台＋SKU＋问题类型只保留一个永久行动编号。刷新更新证据，不按日期复制行动。信号缓解不会自动结案；执行后至少24小时、复查时间到期、有执行后新完整日数据且规则不再触发，才能登记解决。仍未解决需要下一次截止与复查时间。重新出现同类问题，或新期间证据不足时重开原单，进入已触发／待核实队列并保留历史，不会把历史已解决当作当前仍安全。首页待办按责任聚合为一项，避免刷屏。

最初只因资料不足而生成、经核实从未触发的记录，可以由对应复查岗位“核实排除”，提供完整证据及说明，不要求虚构执行。曾经确认触发的记录不能通过此入口绕过执行与复查。页面将信号缓解的记录单列待核对队列，避免挤占今天真实触发问题的位置。

## 数据与计算规则

覆盖五站线上销售。以各站点当地昨天为截止（印尼、泰国、越南 UTC+7；马来西亚、菲律宾 UTC+8），不包含今天未结束的数据。近7天与前7天是连续自然日。只有完整日报／确认零销售日报算完整覆盖；缺报、部分报表与冲销记录不能当作零销量。毛销量不与退货抵消。库存为账面可售减预留，不纳入待上架或隔离。线下销售不并入本模块线上贡献核算。

- **越卖越亏**：近7天实际成交额减财务确认的本SKU本期到岸商品成本、广告、平台佣金及支付、履约、未在成交额扣除的退款与售后净成本。是经营贡献，未扣公司固定费用及所得税，不称净利润。折扣已在成交额，不再重复扣。财务填写实际归属的原币费用，全部未知时留空；只有确认无费用才能填0。绝不把全店广告费复制到SKU，或自动按销量分摊。财务核算与原始销售、日报、整店广告数据摘要绑定；期间变化、冲销、修正或广告来源变化后旧核算失效。非站点本币或缺金额先核实，不强行折算后认定利润。止损后完整日报确认零销量，仍需财务核实是否留有广告等费用；确认无持续损失后才允许复查结案。
- **盈利款快断货**：需核实正贡献、近7天完整销量。情景日均＝近7天毛销量÷7；在当前可售基础上逐批按ETA模拟生产期＋运输期＋复盘周期内的缺口。未知／已逾期ETA不能当作今天到货。补货参考量＝max(0, ceil(日均×周期－可售－周期内有效在途－已有生产量))，再按MOQ及订货倍数向上取整。已有生产量防止重复订货，但其交期未确认时不能抵消近期断货风险；提醒核对、加急或调拨。库存不足提示不是采购指令；无有效ETA时暂不提供确定补货量。供参来自现有SKU／供应策略，仍需人工核对准确性。
- **积压款动销变弱**：两期14天完整日报且有连续上架可售证据；近7天比前7天下降至少30%，同时当前库存覆盖≥60天，或近7天确认零销量。零销量、不足14天在售、缺报与缺货分开。没有库存年龄数据时不认定历史呆滞年限。售后反馈只列记录数，不冒充退货率；流量、转化、竞价尚未接平台数据，需要运营提供报表依据，再选择素材、投放、描述、质量整改或清货方案，不能一律降价。

## 优先级与监督

先按证据可靠性分层（财务＋完整销量、完整运营证据、待核实），再按已知拖延损失、可挽回贡献排序；GMV不参与。跨币种仅使用已有有效CNY参考汇率，最多7天缓存；汇率无效时收益金额未知，不把原币大小混排。参考汇率不是财务结算汇率。

亏损情景：拖延一天损失＝核实7天亏损÷7，未来7天可避免损失上限＝本期亏损，假设销量成本保持不变。断货情景：断货后一天贡献损失＝日均×核实单位贡献；未来7天风险贡献＝预计缺货天数×日均×单位贡献。动作不保证回收该金额。弱动销没有可核实的措施效果时不预设收益，显示待核实。

页面分为已触发、待核实、待分配、待复查、已解决队列，展示负责人、到期状态、协作人、原始核算来源、执行及复查前后证据。当前解释来自确定性规则与人工记录，**没有把业务数据发送给外部AI**。将来AI可改写解释与建议，但不得改写计算数字或绕过权限／复查门槛。

## 运行、存储及验证

`GET /api/business-actions`只读；`POST`明确刷新或人工动作。Node后台启动并每10分钟刷新，在站点午夜跨期后更新；用户可主动更新。源数据版本时钟防止读取过程中变化，以及核算／复查事务期间的竞争；行动记录使用乐观版本防覆盖。数据刷新事务不更改销售、库存、广告、价格、采购或付款。

迁移 `0026_business_actions.sql` 新增行动、财务核算、事件轨迹和源版本表。所有业务写入遵循维护锁，四表纳入既有全量备份恢复；版本时钟懒初始化，避免恢复时冲突。具体负责人确认、诊断、财务、执行、复查、重开均留痕。

验证：规则与真实SQLite迁移、权限、并发、备份恢复测试在 `tests/business-actions.test.mjs`；本地接口及桌面／手机页面验收。第一阶段不连接广告／商品变价接口，也不创建采购指令。
